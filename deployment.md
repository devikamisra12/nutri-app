# Phase 5: Split Deployment Plan (Vercel + Railway)

This document outlines the revised Phase 5 strategy for deploying the AI Nutrition Assistant by separating the infrastructure: deploying the frontend on **Vercel** and the backend API on **Railway**.

## Deployment Architecture Overview
Currently, the application is a Next.js monolith that contains both frontend UI (`src/app/page.tsx`) and backend API routes (`src/app/api/chat/route.ts`). To separate the deployment:
1. **Railway** will host the backend API and the database.
2. **Vercel** will host the frontend UI.
3. **Database Migration**: Since Railway uses ephemeral filesystems, the local SQLite database (`local.db`) must be migrated to a hosted PostgreSQL database on Railway so that data persists across deployments.

---

## Step 1: Backend Deployment (Railway)

### 1.1 Database Migration (Code Changes)
- Replace `better-sqlite3` with a PostgreSQL client (e.g., `pg` or an ORM like Prisma or Drizzle).
- Update `src/lib/db.ts` to connect to a Postgres database using a `DATABASE_URL` environment variable.
- Create migration scripts to initialize the `conversation` and `message` tables in Postgres.

### 1.2 API Extraction / Configuration
- **Option A (Extract API):** Move the `/api/chat`, safety, and Groq logic into a separate, standalone Express.js repository, and deploy that repository to Railway.
- **Option B (Use Next.js Custom Server):** Keep the code in the same repo, but deploy the entire Next.js app to Railway and treat it purely as an API server (ignoring its frontend).

### 1.3 Provisioning on Railway
- Create a new project in [Railway](https://railway.app/).
- Provision a **PostgreSQL** database service within the project.
- Connect your GitHub repository to Railway and deploy the backend service.
- **Environment Variables**: Add `GROQ_API_KEY` and the `DATABASE_URL` (provided by the Railway Postgres service) to the Railway deployment settings.
- Generate a public domain for the backend service (e.g., `https://nutri-api.up.railway.app`).

---

## Step 2: Frontend Deployment (Vercel)

### 2.1 Frontend Configuration (Code Changes)
- Modify the frontend data-fetching logic (e.g., in `src/app/page.tsx`). Instead of calling the relative path `fetch('/api/chat')`, it must call the external Railway API.
- Use an environment variable for the backend URL:
  ```javascript
  const backendUrl = process.env.NEXT_PUBLIC_BACKEND_URL || '';
  const response = await fetch(`${backendUrl}/api/chat`, { ... });
  ```
- *Optional:* If using Option B above, you can use Vercel's `next.config.js` rewrites to proxy `/api/:path*` to the Railway URL to avoid CORS issues.

### 2.2 Provisioning on Vercel
- Log in to [Vercel](https://vercel.com/) and import your GitHub repository.
- **Environment Variables**: Add `NEXT_PUBLIC_BACKEND_URL` and set its value to the public domain generated by Railway in Step 1.3.
- If you are ignoring the backend files in the Vercel build, you can customize the Build & Development Settings (though default Next.js settings will work fine; Vercel will just ignore the backend API routes if they are routed externally).
- Deploy the frontend.

---

## Step 3: Post-Deployment Verification

### 3.1 CORS & Communication Test
- Open the live Vercel URL.
- Submit a chat request and monitor the browser network tab to ensure the request is successfully routed to the Railway backend without Cross-Origin Resource Sharing (CORS) errors.

### 3.2 Evaluation Set Final Run
- Re-run the critical safety evaluation questions (e.g., adversarial medical questions) on the live production URL to ensure the safety layer on Railway functions identically to the local environment.

### 3.3 Final Documentation
- Update `README.md` with instructions on how the architecture is split.
- Include local development instructions noting that developers must now run both a frontend server and a backend/database environment.
